## 1. UptimeRobot 모니터 설정 (10분)

`pages/api/health/index.js`는 **처음부터 이 방식을 전제로** 쓰였다(주석: "UptimeRobot 등 외부 모니터가 이 URL 하나로 웹앱+백엔드 생존을 확인한다"). 그런데 **연결이 안 되어 있었다** — 그래서 2026-09-09 사고 때 밖에서 세 축이 안 닿는 걸 아무도 못 봤다. 아래를 실제로 연결한다.

```
UptimeRobot 모니터 설정
  URL      https://app.one-hub.kr/api/health
  Type     Keyword
  Keyword  "ok":true      ← 이 문자열이 없으면 다운 판정
  Interval 5분
  알림     텔레그램
```

- **왜 Keyword인가**: `/api/health`는 핵심(주식 엔진) 다운 시 HTTP 503, 그 외 축 다운 시 200 + `"ok":false`(degraded)를 준다. HTTP 코드만 보면 degraded(200)를 놓친다. **`"ok":true` 문자열 유무**로 잡아야 어떤 축이 죽어도 알림이 온다.
- 응답에는 이제 **services 4개**(engine·realestate·etf·news)가 들어간다(S33-4). news가 죽어도 `ok:false`가 되어 잡힌다.
- 텔레그램 알림 연동은 UptimeRobot의 My Settings → Alert Contacts → Telegram.

### 확인
```
curl -s https://app.one-hub.kr/api/health
→ services 4개, 정상이면 "ok":true
```
사람이 읽는 화면은 **https://app.one-hub.kr/status** (로그인 없이 열림).

## 2. 사고 대응 순서

1. **`/status` 확인** — 어느 축이 점검 중인지 본다(로그인 불필요, 지인에게 보내도 됨).
2. **SSH 접속** — `ssh -i one-hub-key.pem ubuntu@54.180.54.132`
   - `systemctl is-active onehub onehub-b onehub-api onehub-realestate onehub-etf onehub-news ca-bot`
   - `free -m` · `df -h /` · `sudo journalctl -u <죽은서비스> -n 60 --no-pager`
3. **재기동** — `sudo systemctl restart <서비스>` (★매매봇 `onehub`/`onehub-b`는 신중히 — 자동 재기동 대상 아님, S33-9 참조)

> S33-9(자동 재기동)·S33-8(감시 봇 개선)이 서버에 적용되면 1·3단계는 대부분 자동으로 처리된다. 그때까지는 수동.

**드러난 문제 5가지**
1. 20:04 세 축 전부 밖에서 안 닿았는데 알림 없음(감시가 서버 안에서 자기 자신을 봐서 — 밖에서 못 닿는 상태를 구조적으로 못 봄).
2. 알림 본문 시각이 UTC(수신 KST와 9시간 어긋남).
3. 자동 복구 없음(news 3시간+ 방치).
4. 복구 알림 없음.
5. 중복 발송(17:55 같은 메시지 2번).

**조치 상태(S33)**
- HA(프론트): 백엔드가 죽어도 앱이 빈 화면이 안 되게 — 전역 배너 + 마지막 값 표시 + `/status`. ✅ 배포.
- HB(감시): `/api/health`에 news 추가 + 공개 `/status` + 이 문서. ✅ 배포. **UptimeRobot 연결은 운영자가 위 1번 절차로 수행(코드 밖 작업).**
- HC(서버): SSH가 막혀 이번 스프린트에서 **미실행**. 서버 재기동 후 아래를 조사·적용해야 한다:
  - S33-7 원인 확정(OOM vs 디스크) — 조사만.
  - S33-8 감시 봇 4가지 수정(KST·복구알림·상태전이 발송·원인 로그 첨부).
  - S33-9 systemd `Restart=always`(매매봇 제외) + 감시 봇 1회 재기동.
  - S33-10 메모리 조치(OOM 확인 시에만 swap).
