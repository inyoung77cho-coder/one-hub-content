## 0. 먼저 — 요청 하나는 그대로 만들면 안 됩니다

> *"AI 상세 리포트를 분석하고 엔진에 피드백하여 **자동으로 엔진을 업그레이드**"*

의도는 정확하지만, **이 앱에는 이미 그것을 막도록 만든 안전장치가 있습니다.** `docs/SERVER_COORDS.md` 에 이렇게 적혀 있습니다.

```
배포는 C:\onehub\deploy_auto_trade.ps1 로만. 손 SCP 금지.
게이트 7종(문법 · 버전후퇴 차단 · 장중 · .bak · git · 재시작 · 검증+자동롤백).
실사격 확인: v8.2 배포 시도 → [중단] 버전 후퇴 감지 exit 1.
서버 auto_trade/ 에 로컬 git 도입 — 어떤 SCP도 git diff 로 드러난다.
version_watch.sh 크론이 APP_VERSION 변경을 텔레그램으로 알린다.
```

**실제 돈이 오가는 매매봇**이고, 장중 배포를 막고, 버전 후퇴를 막고, 배포마다 검증 후 자동 롤백하도록 손수 만들어 둔 체계입니다. 자동 업그레이드는 이 일곱 게이트를 전부 우회합니다.

게다가 통계적으로도 위험합니다. 지금 `pages/pwa/accuracy.js:37` 은 이렇게 판정합니다.

```js
const weak = (data.by_reason || []).filter((r) => r.total >= 2 && (r.accuracy_pct ?? 100) < 50)
```

**2건으로 "이 규칙이 약하다"고 결론냅니다.** 동전을 두 번 던져 둘 다 뒷면이 나온 것을 두고 동전을 바꾸는 셈입니다. 이 판정으로 임계값을 자동으로 고치면 **노이즈를 학습**합니다.

### 그래서 이렇게 만듭니다 — 고리는 닫고, 마지막 한 칸만 사람이

```
① 관측  매일의 정확도·차단사유·판단결과를 원장에 적립      ← 자동
② 발굴  표본이 충분한 약한 규칙만 골라 제안 생성            ← 자동
③ 검증  과거 데이터로 재현 — "이 값이 3개월 전부터였다면"   ← 자동
④ 제안  근거·예상효과·되돌리는 법을 함께 제안 원장에 기록    ← 자동
⑤ 승인  AI 페이지에서 사람이 한 번 누름                     ← 사람 ★
⑥ 적용  기존 deploy_auto_trade.ps1 게이트 통과              ← 사람 ★
⑦ 추적  적용 후 성적을 같은 원장에서 계속 재고, 나빠지면
        되돌리기를 먼저 제안                                ← 자동
```

⑦이 핵심입니다. **자기가 만든 변경의 결과를 자기가 채점**하기 때문에 고리가 돌수록 제안이 좋아집니다. 이것이 "스스로 발전"의 실제 구현이고, 사람이 누르는 한 칸은 속도를 거의 늦추지 않습니다.

## 0-3. AI 페이지 역할 재정의

S25에서 **심판석(주간)** 으로 정했습니다. 여기에 한 면을 더합니다.

> **AI 페이지 = 심판석 + 정비소**
>
> | 면 | 질문 | 대상 | 주기 |
> |---|---|---|---|
> | **심판석** | 나와 AI 중 누가 나았나 | 사용자 | 주간 |
> | **정비소** | 엔진이 지난달보다 나아졌나 · 다음에 무엇을 고칠까 | 운영자 | 월간 |

### 사업화에서 중요한 구분

지금은 InYoung 님이 사용자이자 운영자라 둘이 한 화면에 있어도 됩니다. **하지만 유료 사용자가 생기면 정비소의 *과정* 은 보이면 안 됩니다** — 임계값·차단사유·백테스트는 남의 집 엔진룸입니다.

반대로 **정비소의 *결과* 는 사용자에게 보여야 합니다.**

```
운영자에게   RSI 35~45 구간 가중치 +3 → +2 · 표본 41건 · 백테스트 승률 +4.2%p · [승인]
사용자에게   이번 달 AI가 한 번 개선됐습니다 · 매수 판단 정확도 58% → 62%
```

**"내가 돈 내는 AI가 매달 나아지고 있다"** — 이게 구독을 유지시키는 문장입니다. 그러니 정비소는 처음부터 **운영자 게이트 뒤에**, 결과 요약만 밖으로 나오게 만드십시오.

## S28-3 · 규칙별 성적표

### 문제

`accuracy.js:37` 이 **`r.total >= 2`** 로 약한 규칙을 판정합니다. 2건은 표본이 아닙니다.

### 할 일

1. **표본 기준을 `lib/sampleSize.js` 로 통일** — S22-5가 만든 `samplePolicy` 가 이미 30건 기준을 갖고 있습니다. 새 기준을 만들지 말고 그것을 쓰십시오.
   - 30건 미만: **"판정 보류 · N/30"** 으로만 표시. 제안을 만들지 않습니다.
   - 30건 이상: 정확도와 신뢰구간을 함께.
2. **규칙 단위를 코드와 맞추십시오.** `auto_trade/stock_screener.py` 의 실제 가중치는 이렇습니다(242~267행 실측).
   ```
   RSI  45~60 → +4   35~45 → +3   <35 → +1     (모드 A)
   RSI  45~65 → +4   30~45 → +3   <30 → +2     (모드 B)
   거래량비 1.5↑ → +3   1.2↑ → +2
   MA 교차 → +3 / +2
   당일등락 >0 → +1 · 5일등락 >2 → +2 · >0 → +1
   ```
   `by_reason` 의 사유 문자열이 이 규칙들과 **1:1로 대응하는지 확인**하고, 안 되면 대응표를 만드십시오. 대응이 안 되면 "어느 규칙이 약한지" 를 말할 수 없습니다.
3. **정비소 화면에 규칙별 표** — 규칙 · 발동 횟수 · 채점 수 · 정확도 · 최근 30일 추이 · 마지막 변경일(S28-1 원장).

### 합격선

- 30건 미만 규칙에 정확도 숫자가 단정적으로 표시되지 않는다.
- 규칙 이름이 `stock_screener.py` 의 실제 조건과 대응된다.
- 각 규칙의 마지막 변경일이 보인다.

## S28-4 · 제안 생성기

### 할 일

**`auto_trade/improve_proposer.py`(신규)** — 규칙 기반으로만. **예측 모델을 만들지 마십시오.**

제안이 나오는 조건은 셋뿐입니다.

| 조건 | 제안 | 예시 |
|---|---|---|
| 표본 30↑ 규칙의 정확도가 기준보다 **뚜렷이** 낮음 | 가중치 한 단계 낮추기 | `RSI<35 → +1 을 0 으로` |
| 표본 30↑ 규칙이 **뚜렷이** 높음 | 가중치 한 단계 올리기 | `거래량비 1.5↑ → +3 을 +4 로` |
| 손절이 **반복적으로 너무 일찍/늦게** 걸림 | `STOP_LOSS_PCT` 한 단계 | `-5.0 → -6.0` |

### 반드시 지킬 것

- **한 번에 한 개.** 여러 값을 동시에 바꾸면 무엇이 효과였는지 영원히 모릅니다. 대기 중 제안이 있으면 새 제안을 만들지 마십시오.
- **한 단계씩.** `+4 → +2` 같은 도약 금지. 되돌리기가 쉬워야 합니다.
- **적용 후 최소 관측 기간**(예: 20영업일)이 지나기 전에는 같은 대상에 새 제안을 만들지 마십시오.
- **위험 파라미터는 제안 금지** — `MAX_DAILY_LOSS`, `MAX_BUY_AMOUNT`, `IS_REAL`. 이건 손실 한도이지 성능 파라미터가 아닙니다. **자동 제안 대상에서 코드로 배제**하십시오.
- 제안 문장에 **"오를 것이다" 류의 예측을 쓰지 마십시오**(S25에서 정한 원칙).

### 합격선

- 대기 중 제안이 항상 0 또는 1개다.
- 위험 파라미터가 제안에 절대 나오지 않는다(테스트로 확인).
- 표본 미달이면 제안이 0건이다.

# XC — 검증과 승인

## S28-5 · 제안 백테스트

### 할 일

1. **"이 값이 N개월 전부터 적용됐다면"** 을 과거 데이터로 재현합니다. 기존 `trading.db` 의 신호·체결·가격 이력을 씁니다. **새 데이터 소스를 만들지 마십시오.**
2. 결과는 셋만: **판단 건수 변화 · 정확도 변화 · 누적수익 변화.** 지표를 늘리지 마십시오.
3. **한계를 반드시 함께 표기하십시오.**
   - 과거에 차단됐던 종목은 **매수 후 결과를 알 수 없습니다**(반사실). 추정치임을 밝히십시오.
   - 표본 기간이 짧으면 그렇다고 쓰십시오.
   - **백테스트가 좋다고 미래가 좋은 게 아닙니다.** 이 문장을 화면에 상시 두십시오.
4. **개선이 확실하지 않으면 제안을 버리십시오.** 애매한 제안을 사람에게 넘기면 사람이 대충 누르게 되고, 그러면 고리 전체가 무의미해집니다.

### 합격선

- 제안마다 세 숫자와 한계 문구가 함께 있다.
- 개선 폭이 미미한 제안은 승인 화면에 올라오지 않는다.

## S28-6 · 제안 원장과 승인 화면

### 할 일

   ```
   [승인]  [거절]  [나중에]
   ```
3. **승인은 적용이 아닙니다.** 승인하면 **패치 파일과 배포 명령 한 줄**을 만들어 보여주기만 하십시오.
   ```
   승인됨 · auto_trade/stock_screener.py 패치 생성 완료
   적용:  PowerShell 에서  C:\onehub\deploy_auto_trade.ps1
   ```
   **PWA 에서 서버에 직접 쓰지 마십시오. 게이트 7종을 지나야 합니다.**
4. **적용 감지** — `version_watch.sh` 가 버전 변경을 감지하면 해당 제안을 `applied` 로 바꾸고 S28-1 원장에 연결하십시오.
5. **되돌리기** — 적용 후 20영업일 성적이 이전보다 나쁘면 **되돌리기 제안을 먼저** 만드십시오. 이게 ⑦이고, 고리를 안전하게 만드는 부분입니다.

### 합격선

- 승인해도 서버가 즉시 바뀌지 않는다(패치와 명령만 생성).
- 적용 후 원장에 자동으로 이어진다.
- 성적이 나빠지면 되돌리기 제안이 뜬다.
- 거절한 제안은 같은 내용으로 다시 올라오지 않는다.

## S28-10 · 부동산 신고가 정기 탐색과 게시

### 사용자 요구

> AI 운영판을 기반으로 정보를 탐색하고 새로운 정보는 update — 부동산 신고가 등

### 할 일
