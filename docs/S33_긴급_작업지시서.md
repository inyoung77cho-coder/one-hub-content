## 0. 오늘 무슨 일이 있었나 (사실관계 — 추측 아님)

**측정값**

| 시각(KST) | 밖에서 본 상태 (`/api/health`) | 텔레그램 알림 |
|---|---|---|
| 08:00 | — | 🟢 정상 (전날 09-08 기준) |
| 17:55 | — | 🔴 realestate(:5002), news(:5004) — **같은 알림 2번** |
| **20:04** | **engine·realestate·etf 셋 다 TimeoutError 6001ms** | **없음** |
| 21:00 | — | 🔴 news(:5004) |
| 21:14 | 셋 다 up, 22~29ms | — |

**여기서 나온 문제 5가지**

1. **20:04에 세 축이 전부 밖에서 안 닿았는데 알림이 없었다.** engine(:5001) 사망 알림은 오늘 한 번도 오지 않았다.
2. **알림 본문 시각이 UTC다.** 수신 17:55 KST ↔ 본문 "08:55", 수신 21:00 ↔ 본문 "12:00". 정확히 9시간 차이.
3. **자동 복구가 없다.** news는 17:55에 죽어 21:00에도 죽어 있었다 — 3시간 이상 방치.
4. **복구 알림이 없다.** realestate는 그사이 살아났는데 아무 말이 없었다.
5. **중복 발송.** 17:55에 같은 메시지 2번.

**1번의 원인은 코드에 있다.** `scripts/health.sh`:

```bash
curl -s -o /dev/null -w "%{http_code}" "localhost:$p/health"
systemctl is-active onehub onehub-b onehub-api onehub-realestate
```

**점검이 서버 안에서 자기 자신을 본다.** 텔레그램 메시지 형식("서비스: onehub=active…", "포트: 5001/5002/5003/5004 정상")이 이 스크립트와 일치하므로 감시 봇도 같은 방식이다.
서비스는 살아 있는데 **밖에서 못 닿는 상태**는 구조적으로 감지할 수 없다. 그런데 오늘 사용자가 겪은 것이 정확히 그 상태였다.

**그리고 앱이 빈 화면이 된 원인도 코드에 있다.** `pages/pwa/today.js`의 거의 모든 fetch:

```js
.catch(() => {});          // 침묵
.catch(() => setNews([])); // 빈 배열로 위장
```

장애를 삼켜서 카드가 그냥 안 그려진다. 사용자에게는 "앱이 고장났다"로 보인다.
같은 저장소 안에 **올바른 예시가 이미 있다** — `pages/pwa/assets.js:360`:

> `⚠ 증권사 연동 자산을 불러오지 못했습니다 — 이 총자산은 실제보다 적습니다.`

이 태도를 `today.js`에도 적용한다.

### S33-2 · 마지막으로 본 값을 보여준다 (침묵 금지)

**할 일**

`today.js`의 `.catch(() => {})` 를 전수 조사해 **세 가지 중 하나로** 바꾼다.

| 상황 | 처리 |
|---|---|
| localStorage에 마지막 값이 있다 | 그 값을 그리고 **"N시간 전 기준"** 꼬리표를 붙인다 |
| 마지막 값이 없다 | 카드를 지우지 말고 **"지금 불러오지 못했습니다"** 자리표시자를 남긴다 |
| 원래 비어도 되는 것 | 지금처럼 조용히 넘어간다 |

**절대 하지 말 것**: 실패를 빈 배열이나 0으로 위장하는 것. `setNews([])`는 "뉴스가 없다"와 "못 받아왔다"를 구분하지 못한다. 이건 N1 단일 원장 사고와 같은 종류의 실수다.

**대상 파일**: `pages/pwa/today.js` (최우선), `pages/pwa/index.js`, `pages/pwa/assets.js`.
`assets.js:360`이 이미 올바른 형태이므로 **그 문장 톤을 기준으로 삼는다.**

**검증**: 개발 서버에서 `/api/health`가 전부 down을 반환하도록 임시로 막고 `/pwa/today`를 열었을 때 — 헤더·하단탭만 남는 빈 화면이 **아니어야** 한다.

**검증**: `sudo systemctl kill -s SIGKILL onehub-etf` 후 10초 내에 다시 active가 되는지. (etf로 시험할 것 — 죽어도 영향이 가장 작다.)

### S33-10 · 한 서비스가 서버 전체를 죽이지 못하게 — ★원인 확정됨, 반드시 실행

> **2026-09-09 정정.** 이 항목은 원래 "스왑 추가"였다. 조사(S33-7) 결과 **스왑은 이미 2GB 있고,
> 그런데도 OOM이 났다.** 스왑 추가는 대책이 아니다. 아래 내용으로 대체한다.

**조사로 확정된 사실**

```
Sep 09 08:55:49 UTC  oom-kill: task_memcg=/system.slice/onehub-realestate.service, task=uvicorn
                     Killed process 140842 (uvicorn)
                     anon-rss 1,682,288kB (1.68GB) / total-vm 3,877,612kB (3.88GB)
```

| 항목 | 값 | 판정 |
|---|---|---|
| 서버 총 램 | 1,910 MB | uvicorn 하나가 **88%** 를 점유 |
| 평상시 전체 사용량 | 836 MB | 용량 부족 아님 — **한 프로세스의 이상 증가** |
| 스왑 | 2,047 MB (이미 존재) | 있는데도 OOM → 추가는 무의미 |
| 디스크 | 27% (43GB 여유) | 무관 |

**핵심**: 램을 늘려도 시간만 번다. 고칠 것은 두 가지다 — ① 한 서비스가 박스를 죽이지 못하게 막고 ② 왜 부풀었는지 찾는다.

---

**(a) cgroup 메모리 상한 — 먼저 실측하고 값을 정한다**

```bash
systemctl status onehub-realestate | head -20   # Memory: 줄이 평상시 사용량
```

그 값의 **2.5배쯤**을 상한으로 잡아 `onehub-realestate` 유닛의 `[Service]` 절에 넣는다.

```ini
MemoryMax=700M
MemoryHigh=600M
Restart=always
RestartSec=5
```

```bash
sudo systemctl daemon-reload && sudo systemctl restart onehub-realestate
systemctl show onehub-realestate -p MemoryMax   # 적용 확인
```

**효과**: 이상 증가해도 그 서비스만 죽고 5초 뒤 되살아난다. 박스 전체가 멈추지 않는다.
오늘 같은 3시간 전면 정지가 5초짜리 딸꾹질이 된다.

**주의**: `MemoryMax`를 평상시 사용량에 너무 가깝게 잡으면 정상 요청도 죽는다. 실측 없이 숫자를 넣지 말 것.
`onehub-api`, `onehub-etf`, `onehub-news` 에도 같은 방식으로 넣되 값은 각각 실측한다.
**매매봇(`onehub`, `onehub-b`)에는 넣지 말 것** — 주문 중 강제 종료는 별개의 위험이다.

---

**(b) 왜 1.68GB까지 부풀었나 — 추적**

```bash
sudo journalctl -u onehub-realestate --since "today 08:00" --until "today 09:00" -n 200 --no-pager
```

확인할 것:

| 후보 | 확인 방법 |
|---|---|
| apartment.db 전량을 메모리로 올리는 질의 | 08:55 직전 요청 경로. `fetchall()` / pandas `read_sql` 무제한 |
| **공개 API 남용** (`/api/public/re/estimate`) | S31-1로 **로그인 없이 열린** 엔드포인트. 같은 시각 요청 폭주 여부 |
| 장기 누수 | 재기동 후 24시간 RSS 추이 관찰 |

**단정하지 말 것.** 로그를 보기 전에는 어느 쪽인지 알 수 없다. 원인을 찾으면 `docs/S33_결과.md`에 로그 원문과 함께 기록한다.

**(c) 재발 감시**

재기동 후 24시간 동안 RSS 추이를 남긴다(예: cron 10분마다 `ps -o rss= -C uvicorn` 를 파일에 append).
계단식으로 계속 오르면 누수, 특정 요청에서 튀면 질의 문제다. **이 구분이 다음 수정을 결정한다.**

---

**(d) 미해결 — 20:04 KST 전면 불통**

OOM(08:55 UTC = 17:55 KST)만으로는 **11:04 UTC(20:04 KST)에 engine·etf까지 밖에서 안 닿은 것**이 설명되지 않는다.
realestate가 죽으면 오히려 메모리가 반환된다. OOM 기록은 그날 한 건뿐이었다.
서버는 ~11:59 UTC 재부팅으로 복구되었다(`up 35 min` 역산).

```bash
journalctl --list-boots
sudo journalctl -b -1 -n 60 --no-pager     # 직전 부팅의 마지막 60줄
last reboot | head -5
```

정상 종료 메시지가 있으면 사람이 재부팅한 것, 로그가 뚝 끊겨 있으면 **하드 행이며 원인 불명 사고가 하나 더 있는 것**이다.
후자라면 이 항목을 닫지 말고 결과 문서에 미해결로 남긴다.
