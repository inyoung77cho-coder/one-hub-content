## 배치 CA — 주문 중복 위험 ★최우선, 실거래

### S37-1 · POST 재시도를 멱등하게

**지금**

`auto_trade/kis_api.py:58`
```python
def safe_request(method, url, headers=None, params=None,
                 data=None, retries=3, cache_key=None):
    ...
    for attempt in range(retries):   # ← POST도 3회
```

`:216` `buy_order`, `:247` `sell_order` 가 이 함수를 `POST`로 호출합니다. **재시도 사이에 체결·주문 조회가 없습니다.**

**위험**: 주문이 KIS에 접수됐는데 응답만 유실되면(타임아웃·네트워크 끊김) 같은 주문이 한 번 더 나갑니다. 표시 오류가 아니라 **실제 체결 오류**입니다.

**할 일 — 세 가지를 함께**

**(a) POST는 기본적으로 재시도하지 않는다**
```python
def safe_request(method, url, ..., retries=None, cache_key=None, idempotent=None):
    if retries is None:
        retries = 3 if method == 'GET' else 1      # POST 기본 1회
```
GET의 동작은 바꾸지 마십시오.

**(b) 연결 단계 실패와 응답 단계 실패를 구분한다**

`requests.exceptions.ConnectionError`(연결 자체가 안 됨 = 서버에 안 닿음)는 재시도해도 안전합니다. `Timeout`·`ReadTimeout`(보냈는데 답이 없음)은 **접수됐을 수 있으므로 재시도 금지**입니다.

```python
except requests.exceptions.ConnectTimeout:   # 연결 전 실패 → 재시도 가능
except requests.exceptions.ReadTimeout:      # ★ 보낸 뒤 → 재시도 금지
except requests.exceptions.ConnectionError:  # 상황에 따라 다름 — 보수적으로 금지
```

**확신이 안 서면 재시도하지 마십시오.** 주문이 한 번 안 나가는 것보다 두 번 나가는 게 훨씬 나쁩니다.

**(c) 실패를 삼키지 말고 알린다**

POST가 실패했는데 재시도를 안 하면, **그 사실이 텔레그램으로 나가야** 합니다. 조용히 넘어가면 "주문이 안 나갔는데 아무도 모르는" 상태가 됩니다.

```
⚠️ 주문 응답 유실 — 종목 ○○○ 매수 1주
   접수 여부 불확실. KIS 앱에서 주문내역을 확인하십시오.
```

**금지**: 자동으로 주문 조회 후 재주문하는 로직을 만들지 마십시오. 그건 별도 설계가 필요하고, 잘못 만들면 지금보다 위험합니다.

**검증**
```
□ POST 모킹으로 ReadTimeout 발생 → 요청이 1회만 나감
□ GET 은 기존대로 3회 재시도
□ 실패 시 텔레그램 알림이 발송됨
□ ★ 실제 KIS API를 호출하는 테스트를 하지 말 것
□ ★ Claude Code가 서버에 배포하지 말 것 — 코드만 고치고 보고
```

## 배치 CB — 자산 평가가 거짓말하지 않게

### S37-2 · ETF 부분 시세 실패를 감춘다

**지금**

`lib/etfLive.js:90`
```js
if (any) return { krw: sum, live: true, excluded, suspect };
```

`any` 는 **하나라도 평가되면 true**입니다. 세 종목 중 하나만 시세를 받아도 그 하나만 더한 금액을 `live:true`(실시간 정확)로 돌려줍니다.

**Astra가 지적한 것보다 한 겹 더 나쁩니다.** `excluded` 와 `suspect` 는 각각 *평단 10배 이상 어긋남*(S22-1)과 *직전가 대비 급변*(S24-3)만 담습니다. **단순히 시세를 못 받은 종목은 어느 쪽에도 안 들어갑니다** — `q?.price == null` 이면 `forEach` 를 그냥 통과해 흔적조차 남지 않습니다.

즉 **총자산이 실제보다 적게 나오고, 경고도 없습니다.**

**할 일**

```js
const missing = [];   // 신규: 시세를 못 받은 종목
// positions / holdings 루프에서
if (q?.price == null) { missing.push({ ticker, id }); return; }

// 반환
return { krw: sum, live: true, partial: missing.length > 0, missing, excluded, suspect };
```

그리고 **`lib/ledger.js` 가 `partial` 을 받아 경고로 올려야** 합니다. 화면에는 이렇게.

```
⚠ ETF 2종목의 시세를 받지 못했습니다 — 이 금액은 실제보다 적습니다
```

`pages/pwa/assets.js:360` 에 이미 같은 형태의 문구가 있습니다(*"증권사 연동 자산을 불러오지 못했습니다 — 이 총자산은 실제보다 적습니다"*). **그 톤을 그대로 쓰십시오.**

**판단 기준**: 전부 실패하면 지금처럼 백엔드 요약으로 폴백하고 `live:false`. **일부만 실패하면 `live:true` 를 유지하되 `partial:true` 를 반드시 함께** 내보냅니다. 부분 실패를 전체 실패로 바꾸지 마십시오 — 그러면 멀쩡한 종목까지 못 보게 됩니다.

### S37-3 · 총자산 정의를 화면에 적는다

Astra의 J4 지적입니다. `lib/ledger.js:23` 이 **억 단위 소수 둘째 자리**로 중간 반올림합니다. `0.01억 = 100만원`이라 자산군별 반올림 오차가 총액에 쌓입니다.

**지금 당장 계산을 바꾸지 마십시오.** 원 단위 원장으로 옮기는 건 큰 작업이고 회귀 위험이 큽니다.

**대신 이번에는 정의를 명시합니다.**

```
총자산 옆에 작게:  "억 단위 표시 · 자산군별 반올림"
```

그리고 `docs/API_CONTRACT.md`(또는 새 절)에 **총자산 · 순자산 · 운용자산**의 정의를 적으십시오. 셋이 다른 숫자인데 지금 문서에 구분이 없습니다.

| 용어 | 정의 |
|---|---|
| 총자산 | 주식 + ETF + 부동산 + 현금 |
| 운용자산 | 총자산 − 실거주 부동산 |
| 순자산 | 총자산 − 부채 ← **현재 미구현. 그렇게 적을 것** |

**부채 통합은 이번 범위가 아닙니다.** 다만 "순자산"이라는 말을 화면 어디에도 쓰지 마십시오 — 지금 계산은 순자산이 아닙니다.

## 배치 CC — 데이터가 조용히 뭉개지지 않게

### S37-4 · 증권사별 보유 분리

**지금** `lib/stockHoldings.js:38`
```js
const idx = list.findIndex((h) =>
  (h.trader||"A")===trader && h.name===nm && (h.account||"일반")===acct && (h.ccy||"KRW")===ccy);
```
**broker 와 code 가 없습니다.** 그리고 `:44` 에서 `cur.broker = broker || cur.broker` 로 덮어씁니다.

재현: 미래에셋 1주@100 + 한국투자 1주@200 → **2주@150, broker = 한국투자**. 증권사 정보가 사라집니다.

**할 일**

```js
const idx = list.findIndex((h) =>
  (h.trader||"A")===trader &&
  (h.code||"") === (cd||"") &&            // ★ 종목코드 우선
  h.name===nm &&
  (h.broker||"") === (broker||"") &&      // ★ 증권사 분리
  (h.account||"일반")===acct &&
  (h.ccy||"KRW")===ccy);
```

**주의 — 기존 데이터를 깨지 마십시오.**

이미 합쳐진 보유가 사용자 기기에 있습니다. 병합 키를 바꾸면 **같은 종목이 갑자기 둘로 보일 수 있습니다.** 마이그레이션이 필요합니다.

```
· 기존 레코드는 그대로 둔다 (쪼개지 말 것 — 원래 값을 복원할 수 없다)
· 새 입력부터 새 키로 분리
· code 가 빈 기존 레코드는 code 를 무시하고 매칭 (하위 호환)
```

**KIS 중복 제외 로직에 영향이 갑니다.** broker 가 살아나면 연동 보유와 수동 보유의 중복 판정이 달라질 수 있습니다. `lib/allHoldings.js` 와 `lib/ledger.js` 의 중복 제거를 **반드시 함께 확인**하십시오. 이게 이 항목에서 가장 위험한 부분입니다.

| 대형 페이지 분할 (`pwa/index.js` 4,332줄) | 리팩터링. 지금 병목이 아닙니다 |
| 프록시 HTTP 기본값 · 키를 쿼리에 넣는 경로 | 인프라 작업. 별도 |

**`db_logger.py` 항목을 특히 조심하십시오.** Astra 지적(`:25` 신규 테이블에 trader_id 없는데 `:233`·`:248` INSERT는 필요)은 맞을 가능성이 높지만, **운영 DB는 이미 만들어져 돌아가고 있습니다.** init_db 는 빈 DB에서만 실행되므로 현재 장애가 없는 것입니다. 고치려면 운영 스키마를 먼저 떠서 대조해야 합니다.

## 4. Astra 평가 — 계속 쓸 만합니다

앞서 정한 기준으로 판정합니다.

| 기준 | 결과 |
|---|---|
| 새 결함을 찾았나 | **4건 CONFIRMED.** 15개 스프린트 동안 제가 못 잡은 것들 |
| 거짓 지적 비율 | **0건.** 제가 검증한 네 건 모두 사실 |
| UNKNOWN 을 제대로 쓰나 | 규율 있게 씀. 백엔드 미확인을 정확히 표시 |
| 기존 규칙을 지키나 | webpack 고정을 장점으로 인식 |
| 범위를 지키나 | 코드 수정·대규모 리팩터링 제안 없음 |

**그리고 제 오진을 잡았습니다** — 저장소 범위에 대한 제 판단이 틀렸고, 그 오진 때문에 J3(주문 중복)을 놓칠 뻔했습니다.

**이게 독립 검수의 값입니다.** 같은 모델이 쓰고 같은 모델이 검토하면 같은 맹점을 공유합니다.
