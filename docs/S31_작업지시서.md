## 0. 이 스프린트가 바꾸려는 것

S30이 문턱을 낮췄습니다. 스무 명 시뮬레이션에서 이탈이 절반으로 줄었습니다(정착 11 · 부분 4 · 가끔 3 · 이탈 2).

**이제 남은 문제는 기능이 아니라 사람입니다.** 그리고 사람을 들이는 경로가 지금 아예 없습니다.

| 묶음 | 무엇을 | 왜 이 순서인가 |
|---|---|---|
| **AA** | 로그인 없이 쓰는 공개 도구 | **가치를 맛보기 전에 가입을 요구**하고 있습니다. 유입 경로가 0입니다 |
| **AB** | 은퇴·인출 축 | 자산이 가장 크고 지불 능력이 가장 높은 층이 **5일 만에 닫습니다** |
| **AC** | 증권 계좌 개설 제휴 | 구현은 링크 몇 개. **첫 현금**이고 서버비를 넘깁니다 |
| **AD** | 계좌별 보기 | 앱을 가장 오래 쓰는 사람들이 막혀 있습니다 |

각 묶음 끝에서 **검증 → 빌드 → 커밋 → 푸시 → 결과 문서 → 보고 후 정지.**

## 0-2. 반드시 먼저 읽을 것 — 규제와 표현

유료화·제휴가 들어오면 **표현 하나가 규제선을 넘길 수 있습니다.** 이 스프린트 전체에 적용되는 원칙입니다.

> 국내에서 **불특정 다수에게 대가를 받고 투자 조언**을 제공하면 자본시장법상 **유사투자자문업 신고** 대상이 될 수 있습니다.

이 앱이 파는 것을 어떻게 쓰느냐로 갈립니다.

```
규제 가까움 →  "이 종목을 사세요" · "지금이 매수 타이밍"
규제 멂     →  "당신의 판단을 기록하고 채점합니다" · "세금은 이렇게 계산됩니다"
```

**공개 도구와 제휴 문구에 특히 주의하십시오.** 로그인 밖은 불특정 다수입니다.

- 공개 적정가 도구 → **"실거래 기반 통계"** 이지 "적정 매수가"가 아닙니다.
- 제휴 링크 → **"제휴 링크입니다"** 를 반드시 표기하고, 특정 증권사를 권하지 않습니다.
- 모든 계산 화면에 기존 면책 문구(`규칙 기반 참고 정보 · 투자자문이나 특정 종목 권유가 아닙니다`)를 **그대로** 씁니다. 새 문구를 만들지 마십시오.

이건 법률 자문이 아닙니다. 유료화 직전에 전문가 확인이 필요하다는 점을 결과 문서에 남겨 두십시오.

# AA — 로그인 없이 쓰는 공개 도구

## S31-1 · 공개 API 경로

### 지금 상태 (확인 완료)

`middleware.js` 는 **fail-closed 화이트리스트**로 되어 있습니다.

```js
const PROTECTED_API_PREFIXES = [
  "/api/assets/total", "/api/notifications",
  "/api/pwa-",     // 하이픈 계열 전부
  "/api/pwa/",     // pwa/accuracy · pwa/etf/* · pwa/re/* · pwa/sell
  "/api/user/state", …
];
// 목록 밖 /api 는 공개로 통과
```

부동산 API가 `/api/pwa/re/*` 라 **전부 로그인 뒤**입니다. 공개 도구를 만들려면 **목록 밖 경로**가 필요합니다.

### 할 일

1. **`/api/public/re/estimate`(신규)** — 단지명·평형만 받아 실거래 기반 통계를 반환합니다.
   - 기존 `:5002` 엔드포인트를 **재사용**하십시오. 새 계산 로직을 만들지 마십시오.
   - `PROTECTED_API_PREFIXES` 를 **건드리지 마십시오.** 새 경로가 목록 밖이라 자동으로 공개입니다.
2. **레이트 리밋을 반드시 두십시오.** 공개 API는 남용됩니다.
   - IP당 분당 N회. 초과 시 429와 안내 문구.
   - Vercel 캐시(`s-maxage`)를 길게 — 단지 시세는 하루 단위로 바뀝니다. 같은 단지 요청이 백엔드까지 가지 않게 하십시오.
3. **개인정보를 받지도 남기지도 마십시오.** 단지명·평형만. 로그에 IP를 남기지 마십시오.
4. **응답을 최소화**하십시오. 공개 도구가 유료 기능을 통째로 노출하면 가입할 이유가 없어집니다.
   - 공개: 최근 실거래 통계·지역 평균 대비 위치
   - 비공개(가입 후): 내 단지 추적, 갈아타기 비용, 세금, 대장 대비 추이

### 합격선

- 로그아웃 상태에서 `/api/public/re/estimate` 가 200을 반환한다.
- 같은 단지를 연속 호출해도 백엔드까지 가지 않는다(캐시 확인).
- 분당 한도를 넘기면 429가 뜬다.
- `PROTECTED_API_PREFIXES` 가 변경되지 않았다.

## S31-2 · 공개 적정가 페이지

### 할 일

1. **`pages/estimate.js`(신규)** — `www.one-hub.kr/estimate`. `next.config.js` 의 도메인 분기가 이미 마케팅 경로를 `www` 로 보냅니다(`/pwa`·`/api`·`/login` 제외). **설정을 건드릴 필요가 없습니다.**
2. **화면은 셋뿐입니다.**
   ```
   ① 단지명 입력 (자동완성)
   ② 평형 선택
   ③ 결과 — 최근 실거래 · 지역 평균 대비 위치 · 최근 6개월 추이
   ```
   입력 두 개, 결과 한 화면. **로그인·이메일·전화번호를 묻지 마십시오.** 하나라도 물으면 이탈합니다.
3. **디자인은 S26 체계로** — `--fs-*`·`--sp-*`·`Card`. 다만 이 페이지는 **PWA가 아니라 랜딩**이므로 하단 탭·헤더 아이콘은 없습니다.
4. **OG 태그와 사이트맵** — 카톡에 붙였을 때 카드가 뜨고 검색에 잡혀야 합니다. `public/sitemap.xml` 생성 경로에 추가하십시오.
5. **모바일 우선.** 부동산 커뮤니티에서 퍼지면 대부분 폰으로 들어옵니다.

### 함정

- **결과가 없을 때가 많습니다.** 커버리지 밖 단지가 대부분입니다. `아직 이 단지는 데이터가 부족합니다` 라고 정직하게 쓰고, 그때도 **다음 걸음**(관심 단지로 등록하면 데이터가 쌓이면 알려드립니다)을 주십시오. S28에서 "커버리지를 넓히지 않는다"고 정한 원칙은 유지합니다.
- **"적정가"라는 단어를 쓰지 마십시오.** `최근 실거래 기준 통계` 가 정확하고 안전합니다(0-2 참조).

### 합격선

- 로그아웃 상태에서 단지명만 넣어 결과가 나온다.
- 카톡 공유 시 카드가 뜬다.
- 데이터가 없는 단지에서도 화면이 깨지지 않고 다음 걸음이 있다.
- 어디에도 "적정가"·"매수 추천" 류 표현이 없다.

## S31-3 · 가입 전환 경로와 측정

### 할 일

   - **결과를 본 뒤에만** 노출하십시오. 입력 전에 가입을 권하면 지금과 똑같아집니다.
2. **유입 출처를 남기십시오** — `/login?from=estimate&apt=<단지>`. 가입 후 온보딩에서 **그 단지를 미리 채워** 주십시오. "방금 본 그 단지"가 이어지는 경험이 전환을 만듭니다.

   ```
   public_tool_view    공개 도구 결과를 본 사람
   public_tool_signup  거기서 가입한 사람
   ```
   - 공개 페이지는 로그인이 없으므로 **로컬 저장 + 가입 시 서버로 승격**하는 방식이 맞습니다. 익명 식별자를 만들지 말고, 가입 시점에 `from=estimate` 파라미터만 기록하십시오.
4. **운영자 화면(S30-9)에 한 줄 추가** — `공개 도구 조회 N · 가입 전환 M`.

- 공개 도구에서 가입하면 온보딩에 그 단지가 미리 들어 있다.
- 운영자 화면에서 조회 수와 전환 수가 보인다.

# AB — 은퇴·인출 축

## S31-4 · "이 돈으로 몇 년"

### 왜

스무 명 중 한 부장(58)·서 여사(63)의 질문은 이렇습니다.

```
"이 돈으로 몇 년을 살 수 있나"
"연금을 언제부터 얼마씩 받는 게 유리한가"
"배당으로 생활비가 나오나"
```

**앱은 하나도 답하지 않습니다.** 판단 원장·심판석·목표 배분은 전부 **불리는 사람**의 도구이고, 인출률·생활비 커버율 같은 개념이 코드에 없습니다. 서 여사는 5일 만에 닫습니다.

### 할 일

1. **앱에 '단계' 개념을 넣으십시오.** 이게 이 항목의 본체입니다.
   - `onehub_life_stage` — `accumulate`(축적) / `transition`(전환·은퇴 5년 내) / `withdraw`(인출)
   - 온보딩 투자성향 단계(STEP 1)에 **질문 하나**를 더하십시오: `언제쯤 이 돈을 쓰기 시작하실 계획인가요?`
   - `SYNC_KEYS` 등록. 기본값은 `accumulate`(회귀 없음).
2. **`lib/withdrawPlan.js`(신규)** — **순수 산수만.** 예측 모델을 만들지 마십시오.
   ```
   입력  운용자산(기존 ledger) · 월 목표 생활비(사용자 입력) · 연금 월 수령액(사용자 입력)
   출력  월 인출 필요액 = 생활비 − 연금
         연 인출률 = 월 인출액 × 12 ÷ 운용자산
         지속 연수 = 운용자산 ÷ 연 인출액          ← 수익률 0% 가정
   ```
3. **가정을 화면에 크게 밝히십시오.** 이게 정직성의 핵심입니다.
   ```
   시장 수익률 0%·물가 상승 미반영 기준입니다.
   실제로는 수익과 물가에 따라 달라집니다.
   ```
   - **"4% 룰"을 참고선으로 보여주되 권유하지 마십시오** — `연 4% 이하를 권장하는 견해가 있습니다` 정도.
   - 몬테카를로·성공확률 같은 걸 만들지 마십시오. 그건 자문에 가까워지고 표본도 없습니다.
4. **인출 모드일 때 오늘 화면 상단을 바꾸십시오.**
   - 축적기: 지금처럼 `운용자산 + 오늘 조치`
   - 인출기: `이번 달 인출 계획 · 남은 기간` 을 먼저, 조치는 그 아래
   - S26이 만든 `Card`·`SegTabs` 를 쓰고 새 카드를 만들지 마십시오.

### 함정

- **연금 수령 시기 최적화를 계산하지 마십시오.** 국민연금 조기·연기 수령은 제도가 복잡하고 개인 이력에 따라 달라집니다. **국민연금공단 예상 수령액을 사용자가 직접 입력**하게 하고, 앱은 그 숫자로 산수만 하십시오.
- **주택연금도 이번 범위가 아닙니다.** 공식이 공사 기준이라 틀리면 위험합니다.
- 인출 모드 사용자에게 **매일 조치를 요구하지 마십시오.** 그들의 주기는 월간입니다.

### 합격선

- 온보딩에서 단계를 고를 수 있고 기본값은 축적이다.
- 생활비·연금을 넣으면 인출률과 지속 연수가 나온다.
- 가정 문구가 결과와 같은 크기로 보인다.
- 인출 모드에서 오늘 화면 첫 줄이 바뀐다.
- 기존 축적기 사용자 화면이 변하지 않는다(회귀 없음).

## S31-5 · 생활비 커버율

### 할 일

1. **월 현금흐름을 한 줄로.**
   ```
   목표 생활비 320만원
   연금 140  +  배당·이자 45  =  185만원 (58%)
   부족분 135만원 → 자산에서 인출
   ```
2. **배당·이자는 있는 데이터에서만** 뽑으십시오. 보유 종목의 배당 이력이 없으면 **사용자가 직접 입력**하게 하고, 없으면 0으로 두고 `배당 정보를 넣으면 커버율에 반영됩니다` 라고 쓰십시오. **추정하지 마십시오.**
3. **커버율이 오르면 알려주십시오.** 이게 인출기 사용자의 유일한 "매일 볼 이유"입니다 — 다만 매일이 아니라 **월 1회**(S23 `todayCadence` 의 월초 훅에 추가).
4. **ETF 세금 달력(S22-8)과 이어붙이십시오.** 인출기 사용자에게 연금 수령·세금은 같은 이야기입니다.

### 합격선

- 커버율이 근거 숫자와 함께 나온다.
- 데이터가 없는 항목을 추정하지 않는다.
- 월초에 한 번만 알린다.

# AC — 첫 현금

## S31-6 · 증권 계좌 개설 제휴

### 할 일

1. **`lib/partners.js`(신규)** — 제휴처 목록을 **데이터로** 두십시오. 코드에 흩지 마십시오.
   ```
   { id, name, url, note, active }
   ```
   실제 제휴 계약 전에는 `active: false` 로 두고 **화면에 아무것도 뜨지 않게** 하십시오. 계약이 되면 값만 바꿔 켭니다.
2. **놓을 자리는 세 곳뿐입니다.** 앱이 **이미 연동을 권하는 그 자리**입니다.
   - 온보딩 주식 단계 — `증권 계좌가 없으시면` 아래
   - 오늘 화면 — 보유 0건이고 KIS 미연동일 때만
   - 설정 → 연동
   **오늘 화면 상단 배너·팝업·전면 광고는 만들지 마십시오.** 금융 앱에서 광고는 신뢰를 가장 빠르게 깎습니다.
3. **정직성 규칙 — 전부 지키십시오.**
   - `제휴 링크입니다` 를 **작지 않게** 표기.
   - **여러 증권사를 나란히** 두고 순서를 무작위로 돌리십시오. 한 곳만 밀면 추천이 됩니다.
   - `어느 곳을 고르셔도 ONE·HUB 기능은 같습니다` 를 함께.
   - **AI 판단·추천 화면 안에는 절대 넣지 마십시오.** 수익이 판단에 영향을 준다는 오해가 생깁니다.
4. **클릭 측정은 자체 카운터로.** 외부 추적 스크립트를 넣지 마십시오 — CSP·개인정보·성능 전부 나빠집니다. `lib/funnel.js` 에 `partner_click` 을 더하고 운영자 화면에 건수만.

### 함정

- **제휴 계약이 없는 상태에서 링크를 붙이지 마십시오.** 실제 제휴 코드가 없으면 수익도 안 생기고 사용자만 내보냅니다. **`active: false` 로 만들어 두고 계약 후 켜는 것**이 이 항목의 산출물입니다.
- 제휴처 선정은 사업자 판단입니다. **코드는 자리만 만듭니다.**

### 합격선

- `active: false` 상태에서 화면에 아무것도 안 뜬다.
- `true` 로 바꾸면 세 자리에만 뜬다.
- AI 판단 화면에 없다.
- 제휴 표기와 "기능은 같습니다" 문구가 있다.
- 운영자 화면에 클릭 수가 보인다.

# AD — 계좌별 보기

## S31-7 · 전제 확인 후 계좌 모델 정리

### 먼저 — 제 이전 진단이 틀렸습니다

스무 명 분석에서 "최 대표가 A·B를 오가며 성적표가 갈린다"고 썼는데, **코드를 보니 그렇지 않습니다.**

```js
// lib/tenant.js
admin → tenant "A"   ·  친구 → "B"  ·  그 외 신규 카카오 → "u" + kakaoId
// middleware.js
if (t.role === "admin" && (requested === "A" || requested === "B")) effective = requested;
```

**A/B 전환은 운영자 전용**입니다. 일반 사용자는 테넌트가 하나뿐이라 애초에 오갈 수 없습니다.

그러면 여러 계좌를 가진 사용자의 실제 문제는 무엇인가 — **먼저 확인하십시오.**

1. `lib/stockHoldings.js` 의 `account` 필드(기본 `"일반"`)와 `onehub_etf_acct_filter`·`onehub_etf_last_acct` 가 이미 있습니다. **계좌 구분이 데이터에는 존재합니다.**
2. 확인할 것:
   - KIS 연동이 **계좌 하나만** 지원하는가, 여러 개를 받는가
   - 화면(오늘·종합자산·성적표)이 `account` 를 **무시하고 전부 합쳐** 보여주는가
   - ETF는 계좌 필터가 있는데 주식은 없는가
3. **확인 결과를 결과 문서에 적고, 그에 맞춰 아래 중 하나를 하십시오.**

### 할 일 (확인 결과에 따라)

**경우 A — 계좌 구분은 있는데 화면이 무시한다면**
- 종합자산·오늘 화면에 **계좌 필터**를 더하십시오. ETF가 쓰는 방식(`onehub_etf_acct_filter`)과 **같은 패턴**으로.
- 기본은 **전체 합산**, 필터로 계좌별. 지금 잘 쓰는 사용자에게 회귀가 없습니다.
- 성적표는 **합산 유지** — 판단은 계좌가 아니라 사람 단위입니다. 다만 `계좌별 보기` 토글을 두십시오.

**경우 B — KIS 연동이 계좌 하나만 지원한다면**
- 이번 스프린트에서 **다계좌 연동을 만들지 마십시오.** KIS API 인증·계좌 스코프 변경은 매매 엔진을 건드리는 일이고, 실제 돈이 오갑니다.
- 대신 **나머지 계좌를 직접 입력으로 넣는 안내**를 명확히 하십시오. S30이 직접 입력을 이미 1급으로 만들었으니 실용적으로 충분합니다.
- 결과 문서에 **다계좌 연동을 별도 스프린트로 미룬다**고 적으십시오.

### 반드시 지킬 것

- **`lib/tenant.js` 와 `middleware.js` 의 테넌트 로직을 건드리지 마십시오.** 계정 격리의 뿌리입니다.
- `SYNC_KEYS` 의 `_A`/`_B` 하드코딩(10곳)도 **이번엔 손대지 마십시오.** 일반 사용자는 클라이언트에서 항상 `"A"` 를 쓰고 서버가 테넌트로 격리하므로 지금 구조가 실제로는 맞습니다. 이걸 고치려다 계정 데이터가 섞이면 최악입니다.

### 합격선

- 계좌 모델의 실제 상태가 결과 문서에 정확히 적혀 있다.
- 경우 A라면 계좌 필터가 동작하고 기본이 합산이다.
- 경우 B라면 안내가 명확하고 다계좌 연동을 시도하지 않았다.
- 테넌트 로직과 `SYNC_KEYS` 가 변경되지 않았다.
