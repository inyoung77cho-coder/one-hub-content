## 배치 CA — 주문 중복 위험 (S37-1) · ★실거래

### 한 것 — 파일 `auto_trade/kis_api.py`

**(a) POST는 기본적으로 재시도하지 않는다**
- `safe_request(method, url, ..., retries=None, cache_key=None, order_desc=None)` 로 시그니처 변경.
- `if retries is None: retries = 3 if is_get else 1` → **POST 기본 1회, GET은 기존대로 3회.** GET 동작 불변.

**(b) 연결 단계 실패와 응답 단계 실패를 구분한다**
- POST 예외 처리: `ConnectTimeout`(연결 자체 실패 = 서버 미도달, 미접수 확실)만 재시도 후보. `ReadTimeout`(보낸 뒤 무응답)·일반 `ConnectionError`·HTTP 오류는 **재시도 금지(즉시 중단)**.
  ```python
  if not is_get:
      retriable = isinstance(e, requests.exceptions.ConnectTimeout)
      if not retriable or attempt >= retries - 1:
          break
  ```
- "확신이 안 서면 재시도하지 않는다" 원칙 적용. GET은 멱등이라 모두 재시도.

**(c) 실패를 삼키지 않고 알린다**
- 신규 `_notify_order_failure(order_desc, err)`: POST 실패 시 텔레그램(`send_critical`) 발송.
  - **응답 유실**(ReadTimeout·일반 ConnectionError = 접수 여부 불확실): `⚠️ 주문 응답 유실 — 종목 ○○○ 매수 N주 / 접수 여부 불확실. KIS 앱에서 주문내역을 확인하십시오.`
  - **미접수 추정**(ConnectTimeout·HTTP오류 등): `❌ 주문 실패(미접수 추정) — …`
- `buy_order`/`sell_order` 가 `order_desc=f"종목 {stock_code} 매수/매도 {qty}주"` 를 넘겨 **어떤 주문인지** 명시.

### 안 한 것 (지시서가 금지·유보한 것)
- **자동 주문조회 후 재주문 로직 안 만듦** (지시서 금지 — 잘못 만들면 더 위험).
- **서버 배포 안 함** (사용자가 `deploy_auto_trade.ps1` 7게이트로). Claude Code SCP·systemctl 안 함.
- **실제 KIS API 호출 테스트 안 함** (전부 mock).
- `get_access_token`의 별도 `requests.post`(토큰 발급)는 **미변경** — safe_request 미경유이고, 토큰 재발급은 중복돼도 무해(주문 아님).

## 배치 CB — 자산 평가가 거짓말하지 않게

### S37-2 · ETF 부분 시세 실패를 감추지 않는다 — 한 것
- **`lib/etfLive.js`**: `q?.price == null`(시세 못 받음)·환율 없어 환산 불가인 종목을 신규 `missing[]`에 담고, 반환에 `partial: missing.length>0, missing` 추가. 예전엔 `forEach`를 흔적 없이 통과해 총자산이 조용히 과소표시됐음. 부분 실패는 `live:true` 유지 + `partial:true`(전체 실패로 바꾸지 않음). 전부 실패 시에만 백엔드 요약 폴백 `live:false, partial:false`.
- **`lib/ledger.js`**: `live.partial`이면 경고 `ETF_PRICE_MISSING`(`count`) 추가 — `excluded`/`suspect`와 같은 패턴.
- **`pages/pwa/assets.js`**: 총자산 카드에 경고 렌더 — `⚠ ETF N종목의 시세를 받지 못했습니다 — 이 총자산은 실제보다 적습니다`(assets.js:360 톤 그대로).

**검증**(로직 시뮬 3/3 PASS): 3종목 중 1 시세실패 → `live:true·partial:true·missing 1·성공분만 합산`; 전부실패 → `live:false·partial:false`(백엔드 폴백); 펀드 있고 ETF 실패 → `live:true·partial:true`.

**총자산 변화량**: 이 수정은 *경고만 추가*하고 **합산 로직(어떤 종목을 더하는지)은 바꾸지 않았다** → 총자산 숫자 자체는 불변(예전에 빠지던 종목은 여전히 시세가 없어 못 더함, 다만 이제 "적다"고 고지). 실제 환경에서 시세 누락이 있는 날 화면에 경고가 뜨는지는 프로덕션 육안(로그인 게이트·백엔드 데이터 의존).

### S37-3 · 총자산 정의를 화면·문서에 적는다 — 한 것
- **`pages/pwa/assets.js`**: 총자산(운용자산) 숫자 아래 작게 `억 단위 표시 · 자산군별 반올림`(title 툴팁에 J4 반올림 설명).
- **`docs/API_CONTRACT.md`**: "자산 용어 정의(S37-3·J4)" 절 신설 — 총자산/운용자산/**순자산(미구현)** 정의 + 반올림 규칙 + "화면에 순자산이라는 말 쓰지 않는다".
- **"순자산" 화면 사용 확인**: `pages`·`components` 전수 grep = **0건**(이미 안 씀). 계산을 바꾸지 않음(원 단위 원장 전환은 범위 밖).

## 배치 CC — 데이터가 조용히 뭉개지지 않게

### S37-4 · 증권사별 보유 분리 — 한 것 (`lib/stockHoldings.js`)
- `buyStock` 병합 키에 **broker·code 추가**. `trader+account+ccy+broker` 일치 + (양쪽 code 있으면 code 일치 / 한쪽이라도 비면 이름으로 매칭=하위호환).
- **마이그레이션 보호**: 기존 합쳐진 레코드는 쪼개지 않음(원복 불가). 새 입력부터 분리. code 빈 레거시는 code 무시 매칭.

**검증**(실제 `buyStock` 코드, mock localStorage, 4/4 PASS): 미래에셋 1주@100 + 한국투자 1주@200 → **2건 분리·broker 보존**; 같은 증권사 재매수 → **1건 병합·가중평균 150**(쪼개짐 없음); 레거시(code 빈) + code 있는 새입력 → **병합·code 채움**(하위호환).

**★KIS 중복제거 영향 확인**(가장 위험 부분): `lib/allHoldings.js`는 KIS+수동을 **단순 concat**(dedup 안 함)이라 무관. 실제 dedup은 `lib/ledger.js` `isKisDup`(=`code`∈KIS ∧ `broker`∈모호집합[한국투자·기타·빈값])에서만. broker가 살아나면 **명시적 증권사(미래에셋 등)는 모호집합이 아니라 dedup 제외 안 됨** → 예전에 병합으로 broker가 한국투자로 덮여 KIS중복으로 **잘못 제외되던 미래에셋 몫이 이제 총자산에 정상 포함**된다(= dedup이 더 정확해짐, 깨지지 않음).

### S37-5 · `onehub_re_properties` 동기화 — 한 것 (`lib/syncManager.js`)
- `SYNC_KEYS`에 `"onehub_re_properties"` 추가(다른 `onehub_re_*`는 이미 있었음). 미동기화 시 기기 바꾸면 보증금 차감이 사라져 총자산이 달라지던 문제 해소.

**★ledger 총자산 키 ↔ SYNC_KEYS 대조표**(전수):

| ledger 총자산에 쓰는 키 | 용도 | SYNC_KEYS |
|---|---|---|
| `onehub_onboard_assets` | 온보딩 추정치(주식/현금/부동산) | ✅ |
| `onehub_stock_holdings` | 직접입력 주식 | ✅ |
| `onehub_etf_holdings` | ETF 보유 | ✅ |
| `onehub_etf_other` | 기타 금융자산(펀드) | ✅ |
| `onehub_re_properties` | 투자 부동산·보증금 차감 | ✅ **(이번에 추가)** |

→ **총자산에 영향 주는 키는 이제 전부 동기화됨.** 별건: `onehub_etf_pos_qty`(etfHoldings QKEY)는 SYNC_KEYS에 없으나 **`etf.js` 표시용일 뿐 ledger/etfLive가 안 읽어 총자산 무관**(동기화 후보지만 이번 범위 밖 — 결과에 기록).

## 배치 CD — 서비스워커 캐시 계정 분리 (S37-6, INFERRED)

### 재현 판정: **재현됨(코드 경로 전수 확인).** 라이브 2계정 UI 재현은 이 환경(로그인 게이트·SW는 배포 PWA 필요)에서 불가하나, 메커니즘을 코드로 단계별 확정:
1. `lib/trader.js:11` `getTrader()`가 모두 **"A" 기본값** → 사용자 달라도 캐시 URL 동일.
2. `onehub_trader`는 `session.js` `PRESERVE`에 없어 계정 전환 시 삭제 → 다음 사용자도 "A".
3. `public/sw.js:49~56` 금융 GET(`pwa-dashboard`·`assets/total`·`pwa/etf/report`, noCache 정규식에 없음)을 **URL 기준 캐시**.
4. `lib/session.js`가 localStorage만 지우고 **Cache Storage 미삭제**.
5. SWR이 이전 사용자 캐시 응답을 먼저 반환 → **계정 B가 A의 금융 데이터를 잠깐 봄**(남의 금융정보 노출).

### 한 것 (재현됐으므로 수정)
- **`lib/session.js`**: `clearApiCaches()` 신설(정밀 타깃 `onehub-*-api` 캐시만 삭제 — HTML/정적 자산은 사용자 무관이라 미삭제). `logout()`이 캐시 삭제 후 이동.
- **`pages/_app.js`**: 사용자 전환 감지(`enforceUserBoundary`) 시 `clearApiCaches().finally(()=>reload())` — 캐시 삭제 완료 후 새로고침(순서 보장).

> 지시서 "추정만으로 고치지 마라"는 코드 경로 전수 확인으로 충족(추정 아님). 캐시 삭제는 무조건 안전(이전 사용자 사적 응답 제거)이고 금융정보 노출은 심각해 적용함. 배포 후 실기기 2계정 육안 확인 권장.
